# SRMIST Question Paper Office

Separate app for Ramapuram and Trichy PhD entrance question papers. The admissions app is retained as a copy in the parent directory. This app reads that copied admissions database and writes only its own `data` directory.

## Start

From this folder run `npm start`, then open http://127.0.0.1:3100. Dependencies are available from the copied parent codebase's `node_modules`. To move this app independently, run `npm install` and set `ADMISSIONS_DB` to an admissions database containing the campus, institution, department and user tables.

Use existing Admin, Super Admin or HoD credentials. The five assigned research coordinators can track submissions and read papers within their faculty/campus responsibility. Only Common RM coordinators can upload their assigned Common RM categories. Other coordinators, deans and other account holders can sign in to change their portal password only. HoDs can access only their own department and campus; they cannot see other HoDs' upcoming papers. Administrators can view all papers. Login sessions expire after eight hours and reset on restart. Restart after changing account permissions in the admissions database.

The server binds to localhost by default. For a campus deployment, configure HTTPS through a reverse proxy, backups and a protected server. `HOST` and `PORT` configure the listener. Existing account passwords are checked against the copied admissions database using its existing password format.

## Workflow

1. Admin uploads/replaces the two January 2027 Word templates. The supplied files from `Question_Paper_Setting` are seeded on first start.
2. Admin uploads only past-session question papers (January and July 2026), or imports them from the local archive. Confirm the department/campus, session and set for each import because filenames are inconsistent. Archive documents remain downloadable even if their layout cannot be parsed into individual questions.
Administrators upload templates, review submissions and generate papers; they cannot upload January 2027 question papers.

3. HoDs download both templates and upload a January 2027 document for each set. Every upload is checked against readable questions from both past sessions across the matching department group in participating campuses. More than 10 matched uploaded questions rejects the upload without saving it. Exactly 10 is allowed and shown for review. Archives are available for their own campus department.
4. Admin opens each submission in the library, downloads its original Word file, checks all extracted questions and approves it. A full final paper contains 25 Research Methodology and 25 subject questions. Departments assigned Common RM can submit only 25 subject questions; the assigned coordinator supplies the RM section. Generation automatically uses the shared Common RM faculty group across campuses even if a HoD uploads a complete paper with its own RM section. They may also submit a complete 25 + 25 paper. Common RM coordinators submit 25 RM questions.
5. Admin generates final Set A and Set B separately for a department. These are assembled from uploaded questions; the app does not write new questions. Each result is built from the currently uploaded admin template for that set. Shared departments receive exactly 25 questions from each campus (Research Methodology 13/12 and subject 12/13 for final Set A; reversed for final Set B). Subject questions for a department offered at one campus use that campus’s two sets. Assigned Common RM is combined from all coordinator departments in the same faculty across both campuses, even for a single-campus subject department. For Ramapuram Civil Engineering, final Set A therefore has 13 RM from Ramapuram, 12 RM from Trichy and 25 Ramapuram subject questions (38/12 overall); final Set B has 12/13 RM plus 25 Ramapuram subject questions (37/13 overall). Both approved sets from every participating Common RM coordinator are required. Faculty categories remain separate. Both latest submissions must be approved for every participating campus; all source sets contribute. The matrix shows N/A for a campus where the department is absent.
6. The successful generation dialog provides a direct Word download and source-record link; the separate **Generated papers** sidebar tab shows the latest final Set A and Set B for the selected department. Successful generation opens the corresponding department automatically. Opening Generated papers reloads the saved sets from the server; load failures show a retry option. The department dropdown keeps faculty groups separate when their names are the same. Regenerating a set replaces its visible final version; older files and audit records remain stored. A missing set is shown as Not generated yet. Admins can open/download the final Word papers or their source records without generating again. Previously generated papers remain available after signing in again and after deployment. Download the generated Word paper. **View source record** opens a readable table with final question number, question text, source campus/department/coordinator, original Word filename, uploaded set, source question number and correct option. Search or filter by campus/section, expand the original question and options, or download the record as an Excel CSV. The view is administrator-only and also works for previously generated papers. Direct browser links ending in /manifest open a readable source-record page; authenticated API clients can still request JSON with format=json. Inspect the Word layout before printing. Exact duplicate questions are excluded within a paper and against the latest final opposite set. Superseded versions remain stored without consuming the current generation pool. Clicking Generate immediately shows progress. Generation failures identify the requested final set and source filename/question in a dialog and remain visible on the generation page after closing it. A failed source check creates no final record; correct and reupload the named source through its HoD/coordinator account, then approve the replacement. Conceptual repetition needs human review.

## Adding departments

Suresh and Ruby can open **Departments** (also linked from **Upload papers**) and add a department under an existing campus faculty. The super administrator also has access. Choose an existing HoD account from that campus or select **Create a new HoD account**. Enter the name, username, email and a confirmed temporary password (12–128 characters). The new HoD must change this password before accessing papers. An unassigned department can still receive admin-uploaded January and July 2026 archives. An assigned HoD retains access to their existing department and gains access to the new one.

The new department appears in the archive/upload dropdowns, library filters and generation matrix. Common RM requirements follow its campus and faculty automatically. Use the same department name and faculty category across campuses to generate a shared paper; subject questions for a department present at one campus use that campus's two sets, while its matching Common RM faculty group supplies research questions across campuses. Duplicate department names within the same faculty are refused. New HoD accounts, department records and HoD assignments are stored in the question-paper database and restored from the storage bucket on restart; the original admissions accounts/database remain unchanged.

## Upload failures

An upload error remains visible beneath the upload form with the selected filename and the server's reason. Failed submissions retain the selected file and department/session/set for correction and retry. Repeated-question rejection also provides a button to reopen the matched-question table. A confirmed save followed by a failed library refresh is labelled as saved, with instructions to refresh before resubmitting.

Upload Word Document `.docx` files. An older `.doc` file must be opened in Word and saved with **File > Save As > Word Document (.docx)**; changing its extension does not convert it. Template/answer formatting remarks remain advisory for upload, and more than 10 repeated/rephrased questions still rejects a set. Word-format and other validation failures now record the account, filename, selected department/set and reason in the admin-only Activity log under **Upload failed**; repeated-question and set-selection rejections remain **Upload rejected**. Passwords and question text are not included in these upload log details.

For a hosted department that is absent from the local backup, run `bash diagnose-department-uploads.sh` from the current Cloud Shell checkout. This read-only check reports Trichy Clinical Psychology/Cardiac Care department mappings, assigned HoD accounts, temporary-password requirements, saved Cardiac papers, relevant actor-linked activity and recent application messages. It does not change cloud records or print credentials/question text. General application messages may concern other departments; they do not establish which HoD encountered an error without matching account/file evidence.

## Accounts and activity log

Every account holder has a **Change password** page. The username is immutable. A change requires the current password and a confirmed new password of 12–128 characters. The new password is stored as a salted scrypt hash in the question-paper database; the admissions database remains read-only. Subsequent portal logins use the changed password. A password change invalidates all other sessions, including sessions on another app instance.

Administrators have **User accounts** and **Activity log** pages. The account directory shows names, usernames, email addresses, campus, departments, roles and password status. Passwords and password hashes are never returned to the browser. An administrator can reset an account to a temporary password after confirming their own password. The user must change that temporary password before accessing papers. Only a super administrator can reset another super administrator's password.

The activity log records the actor, time in IST and relevant document/department details for uploads, replacements, rejected submissions, approvals, generation, department and HoD account additions, template uploads, sign-ins/sign-outs and password changes/resets. It supports search, action filtering and pagination. Existing paper uploads and custom department additions receive historical entries using the recorded uploader and original timestamp. Actions before logging was introduced can only be reconstructed when that information was saved; passwords are never recorded in logs.

Administrators can **Remove** a paper from the library with a mandatory reason. It is then excluded from screening and generation, and an older version does not automatically become current. This is a recorded soft removal: the document and metadata remain stored for recovery/history. Other users cannot remove papers. Password changes, logs and removal metadata are included in the cloud database snapshot and preserved on restart/redeployment.

## Supported Word format and limitations

Keep `Research Methodology` and `Subject-Specific Questions` headings. A department-specific `Section B: Mathematics` (or another subject name) heading is also recognized, as is a standalone assigned department title such as `Chemistry Questions`. Question numbers in a table’s first column are recognized even when the text is in the next cell. Each question should start with a typed number (for example 1. or 1)) or a Word automatic decimal number, including nested list levels. A sequential number without punctuation is also recognized when it follows a complete option block and has four labelled options ahead. Bare option labels on separate lines, including options consisting of equations, are recognized without skipping adjacent labels. Question blocks extend to the next question number or section heading, independently of option labels. Automatic letter options remain attached to the question; numeric option values are not counted as question numbers. Word list start overrides and restarts are used to retain the displayed question number for answer-key lookup and report references. Mathematical text is included in extraction. Option-formatting differences do not block freshness screening; the administrator checks the original Word document during review. Section headings determine RM versus subject; missing headings produce an unspecified-section count. Numbered template placeholders produce advisory remarks on upload and must be corrected before final generation. Word equations and inline embedded images are preserved. External linked content and unsupported embedded objects are refused during generation. Complex tables, floating layouts and inherited source styles may need adjustment; always verify the final document in Word.

Mathematics combines Ramapuram FET, Ramapuram S&H and Trichy FET into one group, with 25 questions from Trichy and 25 from Ramapuram (13/12 across its two departments). Other generation groups use the institution category and department name to match campuses; Engineering and Science Biotechnology are separate. Unmatched or differently named departments require account mapping correction in the copied admissions database. There is no arbitrary combination of unrelated departments.

The initial templates contain a November 2026 date despite their January 2027 filenames. Upload corrected official templates before distribution. Generated papers are labelled January 2027 without an assumed exam date. Generated papers bold the correct option and include a renumbered answer-key table with Question No. / Correct Option columns, inside the actual uploaded admin Word template. Generation preserves the template logo, cover tables, instructions, footer, fonts, page geometry and answer-key grid, replacing question placeholders and populating the key. Automatically filled institute/faculty and department headings are written in CAPITAL LETTERS. Source options are formatted using the template option paragraphs while equations and embedded images are retained. Missing or structurally unusable admin templates block generation with a clear message. The template date and fixed instructions remain unchanged. Answers are read from each source key, with a uniquely bold source option as a fallback. Missing, ambiguous or conflicting answers are shown by source file, set and the question number displayed in Word; generation waits for correction. Advisory answer remarks include the original stem, the exact key entry, detected bold option letters, label counts and expandable option text. These are automatic reading results for verification, not a judgement that the supplied answer is wrong. Scientific letter references and matching-column entries are excluded from the actual option list when structurally distinguishable. The library and submission review use fresh counts from the original document, including older submissions saved with earlier parser results; approving a submission also refreshes its stored counts. Answers and source question numbers are retained in the JSON record.

View Word file opens/downloads the original document; Review submission shows the counts and screening report. Uploads are `.docx` only, up to 20 MB. Data is persistent in `data/papers.db` and `data/files`; back up both together. No email or external publishing is performed.

## Verification

Run `npm test` and `npm run test:integration`. The integration suite starts an isolated server with synthetic accounts and its own database; it does not change real papers. Tests cover extraction, equal campus distribution, insufficient/duplicate pools, single-campus generation and generated document content. Separate integration checks cover authentication, HoD isolation, templates, uploads, review and downloads.

## Freshness screening

The same screening and submission rules apply to Ramapuram and Trichy, including all Trichy FET, FSH and FMHS Common RM assignments. Count, section, placeholder and option-formatting differences are advisory during submission and approval; the response includes the match table and detected/expected counts together. Option-formatting diagnostics appear in a separate advisory remarks table after the repetition report. They do not block uploads or approval. The administrator’s review displays fresh diagnostics from the original Word file, including for older saved submissions. Fresh readable papers are accepted even with template mismatches. A HoD/coordinator may enter an optional note for the administrator; it is saved with the screening report and retained after review. Up to 10 matched questions are accepted for review; more than 10 are rejected without saving. Missing, incomplete or unreadable archives produce an explicit coverage warning and do not block an upload. Only readable questions can be screened. Administrators must review those warnings before approval. Approval and generation repeat the check against the latest archive versions. Reports show the uploaded set, question number and text alongside the past session, campus, set, question number and text. Each uploaded question counts once even when it has multiple past matches.

Screening runs locally: it compares normalized question stems, word order and a conservative set of synonymous terms. Similarity of at least 80% flags a possible rephrasing; the score is not a probability. Changed numerical values and negation are treated separately. It cannot guarantee semantic equivalence, detect all rephrasings, or compare meaning in diagrams/equations. Human review remains necessary, especially for Tamil, Hindi and technical notation. No confidential exam content is sent to an external AI service.

## Subject-only submissions and template checks

Ramapuram FET and Trichy FET/FSH/FMHS HoDs can submit 25 subject questions while their coordinator’s RM is pending. Structural validation checks numbered counts, section classification and unfilled question placeholders. Counts, section headings, placeholders and option labels do not block uploading or admin approval. Generation still requires the final question totals and reliable source answers. Unused RM placeholders in an otherwise complete subject section are ignored. The answer-key heading is checked with a review warning when absent. This is structural validation, not a font or page-layout comparison with the uploaded template. Generation requires both approved subject sets and, when needed, both approved Common RM sets for every coordinator in the matching Common RM faculty group, independently of where the subject department is offered. Existing generated Word files and their source records remain historical snapshots; generate a new version to apply a changed campus rule. The generation dialog and source record show RM and subject campus counts separately. The source record identifies the actual coordinator paper supplying each RM question.
